Next.js × FastAPI アーキテクチャ

フロントエンド（frontend）とバックエンド（backend）を別フォルダで管理し、FastAPI を src/app/ に置く構成の全体像です。図と DB 構造を中心にまとめています。

この資料の位置づけ: 構成の「あるべき姿」を示す参考資料です。個別機能（Docs Studio）の確定仕様・API・タスクは、Spec Kit の成果物 specs/001-docs-studio/（spec.md / plan.md / tasks.md）が正です。食い違いがあれば specs 側を優先し、こちらを更新してください。
読み方: 評価にとって特に重要な部分に ★ を付けています。リクエストの流れ（3）、DB 構造（7）、状態遷移と操作の一覧（8）、Publish と排他制御（9）、API（10）、テスト計画（12）です。4〜6 節はそれを支える内容です。11 節のデプロイの詳細とAI 機能（計画から除外）は、評価の対象外なので折りたたんであります。

1. 全体像

通常、ブラウザは Next.js サーバーとだけ通信し、FastAPI を直接呼びません。トークンや内部 URL がブラウザに出ず、CORS も原則いりません。

線は実行時の通信を表す。ブラウザから FastAPI を直接叩かないのが基本。

4. バックエンド構成（backend）

レイヤー

Routerapi/v1/routes/*.py — 入力の受け取り、response_model、ステータスコード。ロジックは書かない
Servicedomains/*/service.py — 業務ルール、状態遷移、トランザクション（リクエストごとに1つのセッションと1つの async with session.begin()）。コミットするのはこの層だけ。HTTPException は投げない。テストはこの層を対象にする
Repository（薄く、任意）domains/*/repository.py — 切り出す価値のあるロックとスナップショットの SQL だけ。ORM をなぞるだけのラッパーは書かない。コミットしない
Model / Schemamodels.py（テーブル）と schemas.py（入出力の型）。ORM をそのまま返さない。セッションは expire_on_commit=False

依存は上から下の一方向。例外は AppError 系で投げ、HTTP への変換は例外ハンドラ1か所。

セキュア・バイ・デフォルト

  • ルーターは2つ。書き手のルーターはルーター全体に dependencies=[Depends(require_basic_auth)] を付け、公開のルーター（/public/*）には付けない。新しい書き手のルートは、誰も確認を足さなくても保護される。
  • 認証は、明示的な設定 BASIC_AUTH_ENABLED で切り替えます。本番では必須で、ローカルの実行では既定でオフ（サンプルの環境ファイルがオフにしてある）なので、新規の実行は課題文の記述どおりに動きます。オフのときは、起動時に警告を出します。暗黙のフォールバックにはしません。
  • 認証を有効にして、app.routes を走査するテストが、/api/v1/public と /healthz 以外のルートが、認証情報なしで 401 を返さなければ失敗する。
  • 認証は依存なので、本文の検証より前に動く。401 は 404 と 422 より先。
  • 認証情報は UTF-8 のバイト列にして secrets.compare_digest で、途中で打ち切らずに比べる。Authorization ヘッダーはログに出さない。認証が有効で変数が空なら起動しない（本番では、認証が有効でなければ起動しない）。本番では /docs と /openapi.json を無効にする。CORS のミドルウェアは入れない。

エラーの形（統一し、OpenAPI にも宣言する）

{ "error": { "code": "version_conflict", "message": "...", "details": { "current_draft_version": 7 } } }

コード: unauthorized、not_found、validation_error、version_conflict、empty_content、not_published、version_is_live、slug_conflict。FastAPI 既定の 422 の本文はこの形に置き換え、各ルートがエラー応答を宣言する（responses={404: ..., 409: ...}）ので、生成される TypeScript のクライアントは、エラーを unknown ではなく型つきで扱える。

5.1 Server Action 経由の Basic 認証

  • Server Action はサーバーで動き、自分では Authorization ヘッダーを持たない。受け取ったヘッダーを headers().get("authorization") で読み、API を呼ぶたびに渡す。API クライアントは、ヘッダーを呼び出しごとに受け取り、モジュールのシングルトンには持たせない。
  • 検証するのは FastAPI だけ。proxy.ts は、/studio/** のすべてのリクエスト（action の POST を含む）でヘッダーがあるかを確認するだけで、検証はできない。ヘッダーがないときは、リクエストされたアドレスそのものに 401 と WWW-Authenticate を返す。別のパスへリダイレクトするとループするため（ブラウザは保存した認証情報を、チャレンジされたパスにしか送らない）。
  • API が 401 を返したら、ページは /auth/challenge にリダイレクトする。これは route handler で、認証情報を API で確認する。API が受け付ければ /studio に戻し、そうでなければ WWW-Authenticate: Basic realm="studio" つきの 401 を返して、ブラウザにもう一度尋ねさせる。この確認がないと、誤ったパスワードで、2つのアドレスの間を永久に行き来してしまう（ブラウザは「Throttling navigation」で止めて、空白の画面を表示する）。Server Action は、このレスポンスヘッダーを自分では設定できない。
  • ブラウザは Basic 認証の認証情報を、realm とパスごとに覚える。ログアウトはなく、この範囲では許容する。

5.2 公開ページはキャッシュしない

  • 公開ページは export const dynamic = "force-dynamic"（API の fetch は cache: "no-store"）にする。公開停止が次のリクエストから効き、ビルド時にデータを取りに行かない。キャッシュ層は対象外で、古いページが残ると 404 の要件を破る。
  • API_BASE_URL は、実行時だけのサーバー変数で、NEXT_PUBLIC_* にはしない。env.ts は遅延して（クライアントを作る関数の中で）検証するので、next build には要らない。

5.3 Markdown の描画

  • 保存する本文は Markdown のまま。バックエンドは描画しない。公開側の Server Component がサーバーで描画する（生の HTML は描画せず、rehype-sanitize を使い、リンクは http、https、mailto に限る）ので、読者に Markdown ライブラリは配信しない。
  • 書き手のプレビューは Client Component で、同じ lib/markdown.ts を使うので、プレビューと公開ページは食い違わない。javascript: のリンクと生の <script> をテストで確認する。

5.4 編集画面と競合したときの流れ

  • ページは Server Component で、下書きと draft_version を取得し、小さなクライアントのフォーム（useActionState）に両方を渡す。保存では、フォームを**読み込んだときの** draft_version を送る。取り直した値は送らない。
  • 409 version_conflict のとき、action は書き手の入力を捨てず、サーバー側の現在の版を返す。フォームは両方を見せ、最新を読み込み直すか、新しい版に対して再送するかを選ばせる（FR-16）。
  • Publish や Restore に成功したら、action は新しい draft_version をフォームに返す。

5.5 404 とメタデータ

  • API が 404 を返したら、Server Component は notFound() を呼ぶ。これで本物の 404 ステータスになる。「見つかりません」と 200 で描画することはしない。一度も公開されていない記事と、公開停止の記事は、同じに見える。
  • generateMetadata は、公開中スナップショットから title と description を取る。/studio は noindex。

5.6 スタイル

  • Tailwind CSS だけを使い、コンポーネントライブラリは使いません。落ち着いた配色にアクセントの色は1色、システムフォント、ゆったりした余白、読みやすい本文の幅。ライトテーマのみです。
  • src/components/ui/ に、共通の小さな部品（ボタン、入力欄、テキストエリア、タグ、状態バッジ、空の状態）を置き、キーボードフォーカスを見えるようにし、スマートフォンからデスクトップの幅まで崩れないレイアウトにします。
  • これは、機能とそのテストが済んだあとの、時間を区切った仕上げです（13 節 R16）。見た目は評価されないので、不変条件を遅らせることはありません。

6. 型の合わせ方（API の仕様書から自動生成）

OpenAPI と OpenAI は別物です。 OpenAPI は「API の仕様書を機械が読める形で書く」ための標準的な書式（旧称 Swagger）で、AI とは関係ありません。FastAPI は、書いたコードから自動でこの仕様書を作ってくれます。

なぜ必要か

バックエンドの API が返すデータの形と、フロントエンドが想定している型が食い違うと、画面が壊れても動かすまで気づけません。そこで「バックエンドの定義を正」とし、フロントの型はそこから自動で作ることで、食い違いをなくします。

流れ

① backend: 入出力の型（Pydantic）を変更
→
② FastAPI が API の仕様書 openapi.json を出力
→
③ frontend: 仕様書から TypeScript の型を自動生成
→
④ 型エラーで、直す画面が分かる

コマンド（API を変更したとき）

# backend: 仕様書を出力する
cd backend && uv run python scripts/export_openapi.py

# frontend: その仕様書から型を生成する
cd frontend && pnpm gen:api
  • 生成された型のファイル（frontend/src/lib/api/generated/）は手で編集しない。
  • 各 API に operation_id を付けて、生成される関数名を安定させる。決め方は、すべてのルートに operation_id を明示し、TypeScript 側から見た camelCase にする（listPublicArticles、publishArticle）。基準は specs/001-docs-studio/contracts/openapi.yaml の名前。
  • scripts/export_openapi.py はアプリを組み立てるだけで、DB は要らない。make check-api が openapi.json と型を作り直し、差分があれば失敗する。make test がこれを実行し、pnpm gen:api は make setup に含める。

7. DB 構造（PostgreSQL）

本番は Cloud SQL for PostgreSQL、ローカルは Docker Compose で起動する PostgreSQL 17（db と db-test のサービス）か、Auth Proxy 経由の Cloud SQL を使います。DB は別々にします: 本番、開発用の <name>_dev、テスト用の <name>_test。DDL は backend/db-automation-apply/ に保存します。

核心は、下書きと公開内容を同じ行に混ぜないことです。下書きは articles の draft_* 列に、公開内容は不変の article_versions に置きます。

データの分離: 下書きと公開内容は、同じ行に置かない

下書きは articles.draft_* にあり、Publish がそれを article_versions の新しい不変の行にコピーして、参照を動かします。読者は参照をたどるだけです。
破線の枠は「公開状態」を表す列。draft_* は編集のたびに変わり、article_versions は Publish のときに行が増えるだけです。

DDL（正: backend/db-automation-apply/001_schema.sql）

-- 001_schema.sql
-- Schema for Docs Studio (PostgreSQL). Apply the files in this folder in numeric order.
-- Source of truth for the data model; docs/nextjs-fastapi-architecture.html (section 7) mirrors it.

-- ---------------------------------------------------------------------------
-- articles: the draft and the publication state of one article
-- ---------------------------------------------------------------------------
CREATE TABLE articles (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  slug          TEXT        NOT NULL UNIQUE
                CHECK (char_length(slug) BETWEEN 1 AND 100
                       AND slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$'),
  status        TEXT        NOT NULL DEFAULT 'draft'
                CHECK (status IN ('draft', 'published', 'unpublished')),

  -- Draft content (editable). Never shown to the public side.
  draft_title   TEXT        NOT NULL
                CHECK (char_length(btrim(draft_title)) BETWEEN 1 AND 200),
  draft_body    TEXT        NOT NULL DEFAULT ''
                CHECK (char_length(draft_body) <= 100000),
  draft_tags    TEXT[]      NOT NULL DEFAULT '{}'
                CHECK (cardinality(draft_tags) <= 10),

  -- Optimistic concurrency: bumped by an edit, a Restore, and a Publish that creates a snapshot.
  draft_version INTEGER     NOT NULL DEFAULT 1 CHECK (draft_version >= 1),

  -- Per-article counter used to number snapshots. It never goes down, so numbers are never reused.
  last_version_number INTEGER NOT NULL DEFAULT 0 CHECK (last_version_number >= 0),

  -- Publication state
  current_published_version_id BIGINT,           -- the protected (live) version; kept after Unpublish
  published_at  TIMESTAMPTZ,                      -- first publication time; never changes once set

  created_at    TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),

  -- A never-published article has no pointer and no published_at; every other state has both.
  CONSTRAINT articles_publish_consistency CHECK (
    (status = 'draft'
       AND current_published_version_id IS NULL AND published_at IS NULL)
    OR
    (status IN ('published', 'unpublished')
       AND current_published_version_id IS NOT NULL AND published_at IS NOT NULL)
  )
);

-- ---------------------------------------------------------------------------
-- article_versions: immutable published snapshots
-- ---------------------------------------------------------------------------
CREATE TABLE article_versions (
  id             BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  article_id     BIGINT      NOT NULL REFERENCES articles (id) ON DELETE RESTRICT,
  version_number INTEGER     NOT NULL CHECK (version_number > 0),
  title          TEXT        NOT NULL,
  body           TEXT        NOT NULL,
  tags           TEXT[]      NOT NULL DEFAULT '{}' CHECK (cardinality(tags) <= 10),
  created_at     TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
  UNIQUE (article_id, version_number),
  UNIQUE (article_id, id)              -- target of the composite foreign key below
);

-- An article can only point at one of its own versions, and a referenced version cannot be deleted.
-- With a NULL pointer (never published) the foreign key is not checked (MATCH SIMPLE).
ALTER TABLE articles
  ADD CONSTRAINT articles_current_version_fk
  FOREIGN KEY (id, current_published_version_id)
  REFERENCES article_versions (article_id, id) ON DELETE RESTRICT;

-- ---------------------------------------------------------------------------
-- Guards
-- ---------------------------------------------------------------------------

-- Snapshots are immutable: reject every UPDATE (DELETE stays allowed; the foreign key protects the live one).
CREATE FUNCTION forbid_version_update() RETURNS trigger
LANGUAGE plpgsql SET search_path = pg_catalog AS $$
BEGIN
  RAISE EXCEPTION 'article_versions is immutable';
END $$;

CREATE TRIGGER article_versions_immutable
  BEFORE UPDATE ON article_versions
  FOR EACH ROW EXECUTE FUNCTION forbid_version_update();

-- TRUNCATE bypasses row triggers, so guard it separately.
-- The only exception is the test suite, which resets the data between tests inside a transaction
-- that first runs: SET LOCAL docs.allow_reset = 'on'. The application never sets it, and the
-- application role has no TRUNCATE privilege.
CREATE FUNCTION forbid_version_truncate() RETURNS trigger
LANGUAGE plpgsql SET search_path = pg_catalog AS $$
BEGIN
  IF current_setting('docs.allow_reset', true) = 'on' THEN
    RETURN NULL;
  END IF;
  RAISE EXCEPTION 'article_versions cannot be truncated';
END $$;

CREATE TRIGGER article_versions_no_truncate
  BEFORE TRUNCATE ON article_versions
  FOR EACH STATEMENT EXECUTE FUNCTION forbid_version_truncate();

-- Once published, an article never goes back to "never published", keeps its published_at,
-- and its pointer only moves forward. The slug never changes. updated_at is maintained here.
CREATE FUNCTION articles_guard() RETURNS trigger
LANGUAGE plpgsql SET search_path = pg_catalog, public AS $$
BEGIN
  IF NEW.slug IS DISTINCT FROM OLD.slug THEN
    RAISE EXCEPTION 'slug cannot be changed';
  END IF;

  IF OLD.current_published_version_id IS NOT NULL THEN
    IF NEW.current_published_version_id IS NULL OR NEW.status = 'draft' THEN
      RAISE EXCEPTION 'a published article cannot return to draft';
    END IF;
    IF NEW.published_at IS DISTINCT FROM OLD.published_at THEN
      RAISE EXCEPTION 'published_at cannot change once set';
    END IF;
    IF NEW.current_published_version_id IS DISTINCT FROM OLD.current_published_version_id
       AND (SELECT version_number FROM article_versions WHERE id = NEW.current_published_version_id)
        <= (SELECT version_number FROM article_versions WHERE id = OLD.current_published_version_id) THEN
      RAISE EXCEPTION 'the live version can only move forward';
    END IF;
  END IF;

  NEW.updated_at := clock_timestamp();
  RETURN NEW;
END $$;

CREATE TRIGGER articles_guard_trg
  BEFORE UPDATE ON articles
  FOR EACH ROW EXECUTE FUNCTION articles_guard();

-- ---------------------------------------------------------------------------
-- Indexes
-- (article_versions needs no extra index: UNIQUE (article_id, version_number) already serves it)
-- ---------------------------------------------------------------------------
CREATE INDEX articles_public_idx
  ON articles (published_at DESC, id DESC) WHERE status = 'published';
CREATE INDEX articles_writer_list_idx
  ON articles (updated_at DESC, id DESC);

-- ---------------------------------------------------------------------------
-- Privileges (adjust the role names to your environment; run as the owner / migration role)
-- ---------------------------------------------------------------------------
-- REVOKE UPDATE, TRUNCATE ON article_versions FROM app_role;
-- GRANT SELECT, INSERT, DELETE ON article_versions TO app_role;
-- GRANT SELECT, INSERT, UPDATE ON articles TO app_role;

制約が守る不変条件

原子性を保証するのはトランザクションです。下の制約は、バグや手作業があっても、おかしな状態が保存されないようにするためのものです。

8. 記事の状態遷移

1つの記事の流れ: 各操作で何が変わるか

左から右へ読みます。状態と参照が変わるのは Publish と Unpublish のときだけで、編集と Restore は下書き（と draft_version）だけを変えます。
編集と Restore は draft_* 列を変えるだけで、どの状態でも status と公開中の版は動きません。公開側から見えるのは published のときの「公開中スナップショット」だけです。

9. Publish と排他制御の要点

書き手の操作は、すべて先に記事の行ロックを取る（または1文の条件つき UPDATE にする）。判断は、すべてロックした行に対して行う。ロックの順序は常に「記事の行、次に版の行」なので、操作どうしがデッドロックしない。READ COMMITTED で足りる。REPEATABLE READ にすると、待ちがシリアライズ失敗に変わるので使わない。

Publish: 判断の順序

判断はすべてロックの後に、ロックした行に対して行います。最後の手順より前で失敗すれば、DB は何も変わりません。

Publish（1トランザクション）

BEGIN;
SET LOCAL lock_timeout = '3s';
SELECT a.*, v.title AS live_title,
       v.body AS live_body, v.tags AS live_tags
FROM articles a
LEFT JOIN article_versions v
  ON v.article_id = a.id
 AND v.id = a.current_published_version_id
WHERE a.id = :id
FOR UPDATE OF a;                    -- 0 行: 404

-- 判断はロックの「後」に行う。先に読んだ値は使わない
--  a.draft_version <> :expected  -> 409 version_conflict
--  title か body が空            -> 422 empty_content
--  下書き IS NOT DISTINCT FROM 公開中 (title, body, tags)
--    -> unpublished: status を 'published' に戻す
--       それ以外: 何も書かない        => 200

UPDATE articles
   SET last_version_number = last_version_number + 1
 WHERE id = :id
RETURNING last_version_number;      -- :n

INSERT INTO article_versions
  (article_id, version_number, title, body, tags)
SELECT id, :n, draft_title, draft_body, draft_tags
  FROM articles WHERE id = :id
RETURNING id;                       -- :vid

UPDATE articles SET
  status = 'published',
  current_published_version_id = :vid,
  published_at = COALESCE(published_at, clock_timestamp()),
  draft_version = draft_version + 1
WHERE id = :id;
COMMIT;                             -- 201

ロックの下での行ごとの比較は正確で、ハッシュ列は要らない。比較の相手は公開中のスナップショットだけなので、古い版と同じ内容の下書きでも、新しい版を作る。updated_at は articles_guard トリガーが設定する。

楽観的排他制御（下書き編集）

UPDATE articles SET
  draft_title = :t, draft_body = :b, draft_tags = :g,
  draft_version = draft_version + 1
WHERE id = :id
  AND draft_version = :expected     -- 読んだ時の版
RETURNING draft_version;
-- 0 行: SELECT draft_version FROM articles WHERE id = :id
--   行なし -> 404
--   あり   -> 409 version_conflict
--             details.current_draft_version = その値
A: v5 を読む
B: v5 を読む
A: 保存 → v6
B: 保存(v5) → 409

409 に現在の draft_version を載せ、画面で再読み込みか再送を選ばせる（FR-16）。READ COMMITTED では、B の UPDATE は A を待ち、新しい行に対して WHERE を再評価し、何も更新しない。

Restore（1文）

UPDATE articles SET
  draft_title = v.title, draft_body = v.body,
  draft_tags = v.tags,
  draft_version = draft_version + 1
FROM article_versions v
WHERE articles.id = :id
  AND v.article_id = :id AND v.version_number = :n
  AND articles.draft_version = :expected
RETURNING articles.draft_version;
-- 0 行: 記事か版がなければ 404、それ以外は 409

版の行には触れず、記事がどの状態でも status、参照、published_at も変えない。

Unpublish

SELECT status FROM articles
 WHERE id = :id FOR UPDATE;         -- なければ 404
-- status <> 'published'  -> 409 not_published
UPDATE articles SET status = 'unpublished'
 WHERE id = :id;                    -- 参照と published_at は保つ

版の削除

SELECT current_published_version_id
  FROM articles WHERE id = :id FOR UPDATE;
-- 版の番号がない               -> 404
-- 参照が指す版                 -> 409 version_is_live
DELETE FROM article_versions
 WHERE article_id = :id
   AND version_number = :n;         -- 204
-- SQLSTATE 23503（FK）-> 同じ 409

同時に来た2つの Publish（同じ expected_draft_version）

実装上の注意（async SQLAlchemy）

  • リクエストごとに1つのセッションと1つの async with session.begin() を Service が持つ。expire_on_commit=False。
  • ロックする読み取りは with_for_update(of=Article).execution_options(populate_existing=True) を使う。そうしないと、identity map に残った古いオブジェクトがロックを無効にする。同時実行の経路では、Core の UPDATE … RETURNING を優先する。
  • SET LOCAL lock_timeout と statement_timeout を設定し、ロックのタイムアウトは 503 にする。slug の SQLSTATE 23505 は採番をやり直し（13 節 U15）、23503 は 409 version_is_live に変換して、500 にはしない。
  • プール: pool_size=3、max_overflow=2、pool_pre_ping=True、pool_recycle=1800。Cloud Run のインスタンスが 3 つでも、小さな Cloud SQL の max_connections に収まる。起動時は遅延して接続し、DB が一瞬つながらなくてもコンテナが落ちないようにする。
  • 時刻は clock_timestamp()（文の実行時刻）を使う。ロック待ちをしたリクエストが、前の版より早い時刻にならない。セッションのタイムゾーンは UTC。

  • ストリームで返します。モデルは、プレーンな Markdown を書き、API は、その断片ごとに server-sent event として転送するので、書かれている間に文章が表示されます。最初の断片の前の失敗は、通常のエラー応答（ステータスコードと、いつものエンベロープ）で、ストリームが始まったあとの失敗は error イベントで、届いた文章は残ります。
  • 支出は前払いのクレジットで頭打ちにします。Anthropic のコンソールで、自動チャージをオフにし、ワークスペースの支出上限を設定します。既定の大きさで、1回およそ 2〜3 セントです。
  • Claude のクライアントは、小さなインターフェース（DraftGenerator）の裏に置きます。テストは偽物を使い、ローカルの .env の AI の設定を無視し、API を呼ばないので、make test にキーは要らず、費用もかかりません。実際のモデルでは、所有者がデプロイ先で試したと報告している（詳細は記録していない）。
  • 設定: キーを Secret Manager に anthropic-api-key として保存し、サービスに ANTHROPIC_API_KEY として渡します。AI_ENABLED=true（と、ANTHROPIC_MODEL。既定は claude-sonnet-4-6）を設定します。キーは、コード、イメージ、ログに書きません。キーなしで AI をオンにすると、サービスは起動を拒否します。
  • 歯止め: 既定はオフ。ボタンは常に表示し、機能がオフのときは、案内つきで無効にします。タイトル200文字まで、タグ10個まで、メモ5,000文字まで、指示1,000文字まで。出力のトークン上限。1インスタンスあたり1分に5回（429）。内部の詳細を出さない一般的な失敗（502）。キーも文章も、ログには出しません。入力した文章は、Claude API に送られます。

評価の確認方法

評価者は私たちの Cloud SQL に接続できないので、デプロイ済みの Cloud Run 上の成果物で動作を確認します。URL は README の最初に書き、Basic 認証の認証情報はリポジトリの外で共有します。評価の間は、Cloud SQL と Cloud Run のサービスを動かしておきます。make setup と make dev も、DATABASE_URL で指定した任意の PostgreSQL に対して動きます。

書き手側は Basic 認証（本番では必須、ローカルの実行では既定でオフ）: 課題では認証は Out of Scope ですが、デプロイ先で誰でも編集・公開・削除できてしまうのを避けるため、書き手側（/studio と書き手の API）にだけ Basic 認証を入れます。検証は FastAPI が行い（API を直接呼ばれても守れるように）、Next.js は Authorization ヘッダーを転送します。公開サイトと公開用 API（/api/v1/public/*）は認証なしです。ID とパスワードは環境変数（本番は Secret Manager）で渡します。
