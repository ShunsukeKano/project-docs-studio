1. Overview

In normal operation the browser talks only to the Next.js server and never calls FastAPI directly. Tokens and internal URLs stay out of the browser, and CORS is generally not needed.

4. Backend structure (backend)

Layers

Routerapi/v1/routes/*.py — receives input, sets response_model and status codes. No logic.
Servicedomains/*/service.py — business rules, state transitions and the transaction (one session per request, one async with session.begin()). The only layer that commits. Never raises HTTPException. The tests target this layer.
Repository (thin, optional)domains/*/repository.py — only the locking and snapshot SQL that is worth isolating. Pass-through wrappers around the ORM are not written. Never commits.
Model / Schemamodels.py (tables) and schemas.py (input and output types). ORM objects are never returned as they are. Sessions use expire_on_commit=False.

Dependencies point one way, from top to bottom. Errors are raised as AppError subclasses and converted to HTTP in a single exception handler.

Secure by default

  • Two routers: the writer router carries dependencies=[Depends(require_basic_auth)] for the whole router, and the public router (/public/*) carries none. A new writer route is therefore protected without anyone remembering to add a check.
  • Authentication is switched by the explicit setting BASIC_AUTH_ENABLED: required in production, and off by default for a local run (the example environment file turns it off) so a fresh run behaves as the assignment describes; start-up logs a warning when it is off. It is never an implicit fallback.
  • With authentication enabled, a test walks app.routes and fails if any route outside /api/v1/public and /healthz does not return 401 without credentials.
  • Auth is a dependency, so it runs before body validation: 401 comes before 404 and 422.
  • Compare credentials as UTF-8 bytes with secrets.compare_digest, without short-circuiting; never log the Authorization header; refuse to start if authentication is enabled and a variable is empty (and, in production, unless authentication is enabled); disable /docs and /openapi.json in production; install no CORS middleware.

Error shape (uniform, and declared in OpenAPI)

Codes: unauthorized, not_found, validation_error, version_conflict, empty_content, not_published, version_is_live, slug_conflict. FastAPI's default 422 body is replaced by this envelope, and every route declares its error responses (responses={404: ..., 409: ...}) so the generated TypeScript client types the errors instead of treating them as unknown.

5.1 Basic authentication through Server Actions

  • A Server Action runs on the server and has no Authorization header of its own. It reads the incoming header with headers().get("authorization") and passes it to the API on every call; the API client takes the header per call, never from a module-level singleton.
  • FastAPI is the only validator. proxy.ts only checks that the header is present on every /studio/** request (including action POSTs); it cannot validate. When the header is missing it answers 401 with WWW-Authenticate on the requested address itself, because a redirect to another path would loop (browsers send saved credentials only to the path that challenged them).
  • When the API answers 401, the action surfaces it, and the page redirects to /auth/challenge, a route handler that returns 401 with WWW-Authenticate: Basic realm="studio". A Server Action cannot set that response header itself.
  • Browsers cache Basic credentials per realm and path; there is no logout, which is accepted for this scope.

5.2 Public pages are never cached

  • Public pages use export const dynamic = "force-dynamic" (and cache: "no-store" on the API fetch), so an unpublish takes effect on the next request and the build never fetches data. A caching layer is out of scope, and a stale page would break the 404 requirement.
  • API_BASE_URL is a runtime-only server variable, never NEXT_PUBLIC_*. env.ts validates it lazily (inside the client factory), so next build does not need it.

5.3 Markdown rendering

  • The stored body stays Markdown; the backend never renders it. The public Server Component renders it on the server (no raw HTML, rehype-sanitize, links limited to http, https and mailto), so no Markdown library is shipped to readers.
  • The writer's preview is a Client Component that imports the same lib/markdown.ts, so the preview and the published page cannot differ. Tests cover javascript: links and a raw <script>.

5.4 Editor and the conflict flow

  • The page is a Server Component that fetches the draft and its draft_version and passes both to a small client form (useActionState). Save sends the draft_version the form was loaded with, never a re-fetched one.
  • On a 409 version_conflict the action returns the current server version without discarding the writer's text; the form shows both and lets the writer reload the latest or resubmit against the new version (FR-16).
  • After a successful Publish or Restore the action returns the new draft_version to the form.

5.5 Not found and metadata

  • When the API returns 404, the Server Component calls notFound(), which gives a real 404 status. It never renders a "not found" message with a 200. A never-published and an unpublished article look identical.
  • generateMetadata takes the title and description from the live snapshot; /studio is noindex.

5.6 Styling

  • Tailwind CSS only, with no component library. A neutral palette with one accent colour, a system font stack, generous whitespace and a readable content width; light theme only.
  • A few shared components in src/components/ui/ (button, input, textarea, tag, status badge, empty state), visible keyboard focus, and layouts that work from phone to desktop width.
  • It is a time-boxed polish step after the functionality and its tests (section 13, R16). Looks are not assessed, so it never delays the invariants.

6. Keeping types in sync (generated from the API specification)

OpenAPI and OpenAI are different things. OpenAPI is a standard format (formerly Swagger) for describing an API in a machine-readable way. It has nothing to do with AI. FastAPI generates this specification automatically from the code you write.

Why it is needed

If the shape of the data the backend API returns and the types the frontend expects drift apart, screens break and nobody notices until the app is run. So the backend definition is treated as the source of truth, and the frontend types are generated from it, which removes the drift.

Flow

1. backend: change the input/output types (Pydantic)
→
2. FastAPI writes the API specification, openapi.json
→
3. frontend: generate TypeScript types from it
→
4. Type errors show which screens need fixing

Commands (when the API changes)

# backend: write the specification
cd backend && uv run python scripts/export_openapi.py

# frontend: generate types from that specification
cd frontend && pnpm gen:api
  • Do not edit the generated type files (frontend/src/lib/api/generated/) by hand.
  • Give every API an operation_id so the generated function names stay stable. Convention: set operation_id explicitly on every route, in camelCase for the TypeScript side (listPublicArticles, publishArticle); the names in specs/001-docs-studio/contracts/openapi.yaml are the reference.
  • scripts/export_openapi.py only builds the app, so it needs no database. make check-api regenerates openapi.json and the types and fails on any difference; make test runs it, and pnpm gen:api is part of make setup.

7. Database structure (PostgreSQL)

Production uses Cloud SQL for PostgreSQL; local runs use PostgreSQL 17 started by Docker Compose (the db and db-test services), or Cloud SQL through the Auth Proxy. The databases are separate: production, <name>_dev for development and <name>_test for tests. The DDL is stored in backend/db-automation-apply/.

The key idea is to never mix the draft and the published content in the same row. The draft lives in the draft_* columns of articles; published content lives in the immutable article_versions.

Data separation: drafts and published content never share a row

Drafts live in articles.draft_*; a Publish copies them into a new immutable row of article_versions and moves the pointer. Readers only follow the pointer.
The dashed box marks the columns that hold the publication state. draft_* changes on every edit, while article_versions only gains a row each time an article is published.

DDL (source: backend/db-automation-apply/001_schema.sql)

-- 001_schema.sql
-- Schema for Docs Studio (PostgreSQL). Apply the files in this folder in numeric order.
-- Source of truth for the data model; docs/nextjs-fastapi-architecture.html (section 7) mirrors it.

-- ---------------------------------------------------------------------------
-- articles: the draft and the publication state of one article
-- ---------------------------------------------------------------------------
CREATE TABLE articles (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  slug          TEXT        NOT NULL UNIQUE
                CHECK (char_length(slug) BETWEEN 1 AND 100
                       AND slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$'),
  status        TEXT        NOT NULL DEFAULT 'draft'
                CHECK (status IN ('draft', 'published', 'unpublished')),

  -- Draft content (editable). Never shown to the public side.
  draft_title   TEXT        NOT NULL
                CHECK (char_length(btrim(draft_title)) BETWEEN 1 AND 200),
  draft_body    TEXT        NOT NULL DEFAULT ''
                CHECK (char_length(draft_body) <= 100000),
  draft_tags    TEXT[]      NOT NULL DEFAULT '{}'
                CHECK (cardinality(draft_tags) <= 10),

  -- Optimistic concurrency: bumped by an edit, a Restore, and a Publish that creates a snapshot.
  draft_version INTEGER     NOT NULL DEFAULT 1 CHECK (draft_version >= 1),

  -- Per-article counter used to number snapshots. It never goes down, so numbers are never reused.
  last_version_number INTEGER NOT NULL DEFAULT 0 CHECK (last_version_number >= 0),

  -- Publication state
  current_published_version_id BIGINT,           -- the protected (live) version; kept after Unpublish
  published_at  TIMESTAMPTZ,                      -- first publication time; never changes once set

  created_at    TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),

  -- A never-published article has no pointer and no published_at; every other state has both.
  CONSTRAINT articles_publish_consistency CHECK (
    (status = 'draft'
       AND current_published_version_id IS NULL AND published_at IS NULL)
    OR
    (status IN ('published', 'unpublished')
       AND current_published_version_id IS NOT NULL AND published_at IS NOT NULL)
  )
);

-- ---------------------------------------------------------------------------
-- article_versions: immutable published snapshots
-- ---------------------------------------------------------------------------
CREATE TABLE article_versions (
  id             BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  article_id     BIGINT      NOT NULL REFERENCES articles (id) ON DELETE RESTRICT,
  version_number INTEGER     NOT NULL CHECK (version_number > 0),
  title          TEXT        NOT NULL,
  body           TEXT        NOT NULL,
  tags           TEXT[]      NOT NULL DEFAULT '{}' CHECK (cardinality(tags) <= 10),
  created_at     TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
  UNIQUE (article_id, version_number),
  UNIQUE (article_id, id)              -- target of the composite foreign key below
);

-- An article can only point at one of its own versions, and a referenced version cannot be deleted.
-- With a NULL pointer (never published) the foreign key is not checked (MATCH SIMPLE).
ALTER TABLE articles
  ADD CONSTRAINT articles_current_version_fk
  FOREIGN KEY (id, current_published_version_id)
  REFERENCES article_versions (article_id, id) ON DELETE RESTRICT;

-- ---------------------------------------------------------------------------
-- Guards
-- ---------------------------------------------------------------------------

-- Snapshots are immutable: reject every UPDATE (DELETE stays allowed; the foreign key protects the live one).
CREATE FUNCTION forbid_version_update() RETURNS trigger
LANGUAGE plpgsql SET search_path = pg_catalog AS $$
BEGIN
  RAISE EXCEPTION 'article_versions is immutable';
END $$;

CREATE TRIGGER article_versions_immutable
  BEFORE UPDATE ON article_versions
  FOR EACH ROW EXECUTE FUNCTION forbid_version_update();

-- TRUNCATE bypasses row triggers, so guard it separately.
-- The only exception is the test suite, which resets the data between tests inside a transaction
-- that first runs: SET LOCAL docs.allow_reset = 'on'. The application never sets it, and the
-- application role has no TRUNCATE privilege.
CREATE FUNCTION forbid_version_truncate() RETURNS trigger
LANGUAGE plpgsql SET search_path = pg_catalog AS $$
BEGIN
  IF current_setting('docs.allow_reset', true) = 'on' THEN
    RETURN NULL;
  END IF;
  RAISE EXCEPTION 'article_versions cannot be truncated';
END $$;

CREATE TRIGGER article_versions_no_truncate
  BEFORE TRUNCATE ON article_versions
  FOR EACH STATEMENT EXECUTE FUNCTION forbid_version_truncate();

-- Once published, an article never goes back to "never published", keeps its published_at,
-- and its pointer only moves forward. The slug never changes. updated_at is maintained here.
CREATE FUNCTION articles_guard() RETURNS trigger
LANGUAGE plpgsql SET search_path = pg_catalog, public AS $$
BEGIN
  IF NEW.slug IS DISTINCT FROM OLD.slug THEN
    RAISE EXCEPTION 'slug cannot be changed';
  END IF;

  IF OLD.current_published_version_id IS NOT NULL THEN
    IF NEW.current_published_version_id IS NULL OR NEW.status = 'draft' THEN
      RAISE EXCEPTION 'a published article cannot return to draft';
    END IF;
    IF NEW.published_at IS DISTINCT FROM OLD.published_at THEN
      RAISE EXCEPTION 'published_at cannot change once set';
    END IF;
    IF NEW.current_published_version_id IS DISTINCT FROM OLD.current_published_version_id
       AND (SELECT version_number FROM article_versions WHERE id = NEW.current_published_version_id)
        <= (SELECT version_number FROM article_versions WHERE id = OLD.current_published_version_id) THEN
      RAISE EXCEPTION 'the live version can only move forward';
    END IF;
  END IF;

  NEW.updated_at := clock_timestamp();
  RETURN NEW;
END $$;

CREATE TRIGGER articles_guard_trg
  BEFORE UPDATE ON articles
  FOR EACH ROW EXECUTE FUNCTION articles_guard();

-- ---------------------------------------------------------------------------
-- Indexes
-- (article_versions needs no extra index: UNIQUE (article_id, version_number) already serves it)
-- ---------------------------------------------------------------------------
CREATE INDEX articles_public_idx
  ON articles (published_at DESC, id DESC) WHERE status = 'published';
CREATE INDEX articles_writer_list_idx
  ON articles (updated_at DESC, id DESC);

-- ---------------------------------------------------------------------------
-- Privileges (adjust the role names to your environment; run as the owner / migration role)
-- ---------------------------------------------------------------------------
-- REVOKE UPDATE, TRUNCATE ON article_versions FROM app_role;
-- GRANT SELECT, INSERT, DELETE ON article_versions TO app_role;
-- GRANT SELECT, INSERT, UPDATE ON articles TO app_role;

Invariants and what protects them

Atomicity comes from the transaction; the constraints below stop bad states from being stored even if a bug or a manual change tries.

Guarding in the application and again in the database means bugs or manual operations cannot leave inconsistent data behind. Alembic autogenerate does not create the circular FK, the triggers or the CHECKs correctly, so the DDL is written by hand in db-automation-apply/.

9. Publish and concurrency control: the essentials

Every writer operation takes the article row lock first (or is a single conditional UPDATE), and all decisions are made against the locked row. The lock order is always article row, then version rows, so operations cannot deadlock each other. READ COMMITTED is enough; do not use REPEATABLE READ, which would turn these waits into serialization errors.

Publish: the order of decisions

Every decision is made after the lock, against the locked row. Anything that fails before the final step leaves the database unchanged.

Publish (one transaction)

BEGIN;
SET LOCAL lock_timeout = '3s';
SELECT a.*, v.title AS live_title,
       v.body AS live_body, v.tags AS live_tags
FROM articles a
LEFT JOIN article_versions v
  ON v.article_id = a.id
 AND v.id = a.current_published_version_id
WHERE a.id = :id
FOR UPDATE OF a;                    -- 0 rows: 404

-- decide AFTER the lock, never from an earlier read
--  a.draft_version <> :expected  -> 409 version_conflict
--  title or body empty           -> 422 empty_content
--  draft IS NOT DISTINCT FROM live (title, body, tags)
--    -> unpublished: set status = 'published'
--       otherwise: no write            => 200

UPDATE articles
   SET last_version_number = last_version_number + 1
 WHERE id = :id
RETURNING last_version_number;      -- :n

INSERT INTO article_versions
  (article_id, version_number, title, body, tags)
SELECT id, :n, draft_title, draft_body, draft_tags
  FROM articles WHERE id = :id
RETURNING id;                       -- :vid

UPDATE articles SET
  status = 'published',
  current_published_version_id = :vid,
  published_at = COALESCE(published_at, clock_timestamp()),
  draft_version = draft_version + 1
WHERE id = :id;
COMMIT;                             -- 201

A row-wise comparison under the lock is exact; no hash column is needed. The comparison is with the live snapshot only, so a draft equal to an older version still creates a new version. updated_at is set by the articles_guard trigger.

Optimistic concurrency (editing the draft)

UPDATE articles SET
  draft_title = :t, draft_body = :b, draft_tags = :g,
  draft_version = draft_version + 1
WHERE id = :id
  AND draft_version = :expected     -- the version that was read
RETURNING draft_version;
-- 0 rows: SELECT draft_version FROM articles WHERE id = :id
--   no row -> 404
--   else   -> 409 version_conflict
--             details.current_draft_version = that value
A: reads v5
B: reads v5
A: saves → v6
B: saves (v5) → 409

The 409 carries the current draft_version, and the screen lets the writer reload or resubmit (FR-16). Under READ COMMITTED, B's UPDATE waits for A, re-checks its WHERE clause against the new row and updates nothing.

Restore (one statement)

UPDATE articles SET
  draft_title = v.title, draft_body = v.body,
  draft_tags = v.tags,
  draft_version = draft_version + 1
FROM article_versions v
WHERE articles.id = :id
  AND v.article_id = :id AND v.version_number = :n
  AND articles.draft_version = :expected
RETURNING articles.draft_version;
-- 0 rows: 404 if the article or version is missing, else 409

It touches no version row and none of status, the pointer or published_at, whatever the article's state.

Unpublish

SELECT status FROM articles
 WHERE id = :id FOR UPDATE;         -- 404 if missing
-- status <> 'published'  -> 409 not_published
UPDATE articles SET status = 'unpublished'
 WHERE id = :id;                    -- pointer, published_at kept

Delete a version

SELECT current_published_version_id
  FROM articles WHERE id = :id FOR UPDATE;
-- version number missing        -> 404
-- it is the pointer's version   -> 409 version_is_live
DELETE FROM article_versions
 WHERE article_id = :id
   AND version_number = :n;         -- 204
-- SQLSTATE 23503 (FK) -> the same 409

Two Publish requests at the same time (same expected_draft_version)

Implementation notes (async SQLAlchemy)

  • One session and one async with session.begin() per request, owned by the Service; expire_on_commit=False.
  • Locking reads use with_for_update(of=Article).execution_options(populate_existing=True), otherwise a stale object in the identity map defeats the lock. Prefer Core UPDATE … RETURNING on the concurrency paths.
  • SET LOCAL lock_timeout and statement_timeout; map a lock timeout to 503. On SQLSTATE 23505 for the slug, retry the numbering (U15); map 23503 to 409 version_is_live; never return a 500.
  • Pool: pool_size=3, max_overflow=2, pool_pre_ping=True, pool_recycle=1800, so three Cloud Run instances stay within a small Cloud SQL instance's max_connections. Connect lazily so a database blip at start-up does not kill the container.
  • Timestamps use clock_timestamp() (statement time), so a request that waited for the lock does not get an earlier time than the previous version. The session time zone is UTC.

AI draft generation with the Claude API (excluded; only if time remains)

The API on Cloud Run can call the Claude API. Calling a pay-as-you-go cloud service could be hit without limit and run up an unbounded bill, so the cost is capped with prepaid credit: only a fixed amount is deposited, and the feature simply stops working when it is used up. It is excluded from the planned implementation and from the assessed scope, and is added only if time remains after the core features, the invariant tests, the README and the adopted optional features are all done (section 13, R15).

Edit form: "Generate a draft" + topic
→
POST /ai/draft (Basic auth)
→

→

→

→
Writer saves with PATCH (expected_draft_version)
  • It never writes. The endpoint only returns a proposal. The text enters the draft through the normal edit, so the invariants are untouched, and nothing is published until the writer publishes.
  • Spending is capped by the prepaid credit. In the Anthropic Console, keep automatic reload off and set a workspace spend limit (to be confirmed when it is built). When the credit is used up, the route returns 503 ai_unavailable and the rest of the site is unaffected.
  • The Claude client is behind a small interface (DraftGenerator). Tests use a fake, so make test needs no key and costs nothing.
  • Setup: store the key in Secret Manager as anthropic-api-key and pass it as ANTHROPIC_API_KEY; set AI_ENABLED=true and ANTHROPIC_MODEL (a small, inexpensive model, chosen and confirmed when it is built). The key is never written in code or logged. Cloud Run needs no extra permission for this.
  • Further guards: off by default; 30 second timeout; limits on input length and output tokens; a per-instance rate limit; the instance cap; the prompt text is not logged in full.
  • The output is treated like any other input (tags lowercased and limited to 10, title 200 characters, body 100,000) and rendered through the same sanitizer (U7), so generated text cannot inject HTML. The topic text is sent to the Claude API.

How the work is assessed

Assessors cannot reach our Cloud SQL, so they verify the behaviour on the deployed Cloud Run site. The URL is the first thing in the README, and the Basic authentication credentials are shared outside the repository. Cloud SQL and the Cloud Run services must be running while the work is assessed. make setup and make dev still work against any PostgreSQL given by DATABASE_URL.

The writer side uses Basic authentication (required in production, off by default for a local run): Authentication is Out of Scope in the assignment, but to avoid letting anyone edit, publish or delete on the deployed site, Basic authentication is added to the writer side only (/studio and the writer API). FastAPI does the verification (so the API is protected even when called directly), and Next.js forwards the Authorization header. The public site and the public API (/api/v1/public/*) need no authentication. The ID and password are supplied through environment variables (Secret Manager in production).
