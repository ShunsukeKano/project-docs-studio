SummaryWriters edit freely without changing what readers see, by design

SituationInternal writers draft, edit, publish and take down articles; readers see only published ones on a public site.
ComplicationIf a draft and the published text share one row, editing leaks into what readers see, a published text can change, and two people acting at once overwrite each other or publish twice.
QuestionHow can writers edit freely while what readers see stays frozen and consistent?
AnswerKeep drafts and snapshots in separate tables, publish in one transaction, control concurrent writes by a version check and a row lock, and let the database enforce the rules again.
DirectionJudge the design by why it cannot break, not only by what works. Publish and concurrency (slides 8-11) is where I would like the most discussion.
TakeawayEdit freely, publish safely, and let the database back it up.

Database structureTwo tables: editing never touches what readers see, snapshots never change

articles: one row per article, holds the draft
articles
  slug, status  ('draft' | 'published' | 'unpublished')
  draft_title, draft_body, draft_tags   -- editable
  draft_version        INT NOT NULL DEFAULT 1   -- edit token
  last_version_number  INT NOT NULL DEFAULT 0   -- never goes down
  current_published_version_id BIGINT           -- the live pointer
  published_at         TIMESTAMPTZ              -- first publication
  CONSTRAINT articles_publish_consistency CHECK (
    (status = 'draft' AND pointer IS NULL
                      AND published_at IS NULL)
    OR (status IN ('published','unpublished')
        AND pointer IS NOT NULL
        AND published_at IS NOT NULL))
article_versions: one row per snapshot
article_versions
  id  BIGINT IDENTITY PRIMARY KEY
  article_id  BIGINT NOT NULL
              REFERENCES articles ON DELETE RESTRICT
  version_number INT NOT NULL CHECK (> 0)
  title, body, tags
  UNIQUE (article_id, version_number)
  UNIQUE (article_id, id)   -- target of the FK below

ALTER TABLE articles ADD CONSTRAINT
  articles_current_version_fk
  FOREIGN KEY (id, current_published_version_id)
  REFERENCES article_versions (article_id, id)
  ON DELETE RESTRICT

Publish and concurrency (1/4)Publish decides on a locked row, then writes everything in one transaction

OrderCheckIf it fails
1Lock the article row (FOR UPDATE)404 no such article
2expected_draft_version equals the row’s409 version_conflict
3Title and body are not empty422 empty_content
4Draft equals the live snapshot?200, nothing new (idempotent)
5Counter +1 · insert snapshot · move pointer, status, published_atall or nothing: any failure rolls back
The lock: lock_article_for_publish
SELECT a.id, a.status, a.draft_*, a.draft_version,
       a.published_at, v.version_number, v.title, v.body, v.tags
FROM articles a
LEFT JOIN article_versions v ON v.id = a.current_published_version_id
WHERE a.id = :id  FOR UPDATE OF a
The lock
Lasts untilCOMMIT or ROLLBACK; plain reads are not blocked
Lock orderarticle row, then version rows: no deadlock
Decides onthe locked row, never a value read earlier

Publish and concurrency (4/4)Restore never changes what readers see, and the live version can’t be deleted

RestoreDelete a version
DoesCopies a snapshot into the draft columns (one UPDATE)Removes one snapshot row, after the same row lock as Publish
Never changesSnapshots, status, pointer, published_atThe live version: 409 version_is_live, also after Unpublish
Checkexpected_draft_version → 404 or 409Live? → 409. Second defence: foreign key ON DELETE RESTRICT (23503 → 409)
Readers seeNothing, until the writer presses Publish (a new version)Nothing changes
SQL
UPDATE articles SET draft_title = v.title, draft_body = v.body,
       draft_tags = v.tags, draft_version = articles.draft_version + 1
FROM article_versions v
WHERE articles.id = :id AND v.article_id = :id AND v.version_number = :n
  AND articles.draft_version = :expected
-- after the same row lock as Publish, and the live check
DELETE FROM article_versions
WHERE article_id = :id AND version_number = :n
